# Roles y permisos — plan de implementación

> Se ejecuta en esta sesión, tarea por tarea, con TDD (node --test en la API, vitest en el
> frontend). Cada tarea termina con sus tests en verde y un commit en `feat/roles`.

**Objetivo:** reemplazar el interruptor de admin por roles con permisos (spec abajo).

**Arquitectura:** el catálogo, las dependencias y el permiso de cada ruta viven en
`api/permissions.js` (puro). El dispatcher de `server.js` guarda la clave de la ruta en el
pedido, y `requireAdmin` pasa a exigir el permiso que el catálogo le asigna a esa ruta (si una
ruta no tiene permiso, se niega). Así los 71 handlers no cambian de forma y un test verifica la
cobertura. Roles en la tabla `roles`, `users.role_id`.

**Spec:** `docs/superpowers/specs/2026-10-01-roles-design.md`

## Restricciones globales

- Node `node:http` + `node:sqlite`, sin dependencias nuevas. React + Zustand en el frontend.
- Textos de la interfaz en español (claves en español pasan por `t()`), "lauyim" en minúscula.
- `PUT /api/admin/members/settings` ya es solo del owner (`requireOwner`): queda así (corrige el spec).
- Clientes viejos: `/api/me` sigue mandando `admin` (= es del staff) y `staff` (= exento de cuota).

### Tarea 1: `api/permissions.js`

**Archivos:** crear `api/permissions.js`, `api/permissions.test.js`.

**Produce:**
- `PERMISSIONS`: lista `{ code, area, name, help, requires: [] }` en el orden de la pantalla.
- `PERMISSION_CODES`, `withDependencies(codes) → codes` (agrega lo requerido, ordena, filtra desconocidos),
  `withoutDependents(codes, removed) → codes` (apagar uno apaga los que dependen de él).
- `ROUTE_PERMISSIONS`: `{ 'GET /api/admin/users': 'members.view', … }` para cada ruta `/api/admin/*`.
- `DEFAULT_ROLES`: los cuatro roles de fábrica (`id`, `name`, `color`, `permissions`, `builtin`).
- `ADMIN_ROLE_ID = 'admin'`.
- `permissionsOf({ owner, envAdmin, role }) → codes`; `can(perms, code)`; `isSubset(a, b)`.
- `validateRole(body, { existingNames }) → { value } | { error, field }`.

Tests: dependencias en las dos direcciones, owner y envAdmin con todo, rol sin permisos,
`validateRole` (nombre 1–30, repetido sin distinguir mayúsculas, color, permisos desconocidos
filtrados, dependencias completadas, `feeExempt` por defecto true), los cuatro roles de fábrica.

### Tarea 2: base de datos

**Archivos:** `api/database.js`, test `api/roles-db.test.js`.

**Produce:** tabla `roles`, columna `users.role_id`, siembra con la marca `roles_seeded` y migración
de `admin = 1` (sin owner) → `admin`. Funciones: `getRoles()` (con `members` = cantidad),
`getRole(id)`, `saveRole({ id?, name, color, permissions, feeExempt })` → rol,
`deleteRole(id)` (sus usuarios a NULL, en transacción), `setUserRole(userId, roleId | null)`.
`createUser({ admin: true })` (owner, demo, tests) asigna el rol Administrador.

Tests: siembra única (borrar uno y reiniciar no lo recrea), migración del admin viejo, conteo,
borrar deja a los usuarios sin rol.

### Tarea 3: API

**Archivos:** `api/server.js`, tests `api/roles.http.test.js`, `api/route-permissions.test.js`.

- Dispatcher: `req.routeKey = routeKey`.
- `permsOf(user)`, `can(user, code)`, `isStaff(user)`, `isFeeExempt(user)`.
- `requireAdmin` → exige `ROUTE_PERMISSIONS[req.routeKey]`; sin entrada, 403.
- `isAdmin` → `isStaff`; `isRealStaff` → `isFeeExempt` (cuotas).
- Salud: sin `health.view`, `GET /api/admin/user` sin peso ni `bw`, `GET …/routines` sin lesiones.
  La regla de consentimiento existente aplica a cualquier staff.
- Salida del ingreso físico: `can(user, 'checkin.operate')`.
- Desactivar: a alguien con rol no (`role_undisableable`).
- `/api/me`: `role`, `permissions`, `admin` = `isStaff`, `staff` = `isFeeExempt`.
- `GET /api/admin/users`: cada usuario con `role` (`{ id, name, color }` o null).
- Rutas nuevas: `GET /api/admin/roles`, `POST /api/admin/users/role`, `POST /api/owner/roles/save`,
  `POST /api/owner/roles/delete`, `POST /api/owner/audit/clear`. Se van `POST /api/owner/user/admin`
  y `POST /api/admin/audit/clear`.

Tests: cobertura (cada ruta `/api/admin/*` de `server.js` está en `ROUTE_PERMISSIONS` y viceversa);
HTTP: recepción cobra y no ve nutrición, nutricionista sin peso si no tiene salud, asignar solo roles
incluidos, owner CRUD, borrar rol, `/api/me`.
